The Problem

Today

✕Agents write e2e tests but dev server isn't running — tests fail for wrong reason
✕Engine retries nodes that can never pass without npm install or database up
✕User must manually start services before specwork go — easy to forget
✕No framework detection — agents don't know if Playwright or Cypress is available

✓Detection engine reads package.json + docker-compose and sets up everything

How It Works
Detect
Scan package.json, docker-compose.yaml, .env.example, and framework configs. Runtime-probe available tools. Generate sandbox.yaml with detected services.
Check Ports
Scan declared ports for conflicts. If port 3000 is already in use, warn user: reuse existing service, pick alternate port, or abort. Never kill user processes.
Init Services
Run setup steps in dependency order. Foreground first (npm install), then background (npm run dev). Poll ready-checks until services respond. Write PIDs to state.json.
Agent Runs
Test-writer or implementer runs with services available. .env.test generated from .env.example with test-safe defaults. Verification checks execute against live environment.
Teardown
After verify completes, kill only sandbox-started PIDs. Run teardown commands, clean temp paths, remove state.json. User's own services untouched.

Watch Out For

Engine State Machine Change

impl-7 modifies SKILL.md — the state machine table that drives all workflow execution. Any error here breaks specwork go for every change. Must be tested manually after implementation.

Process Lifecycle on CI

Background process management (PID tracking, ready-checks, SIGTERM) behaves differently across macOS and Linux. process.kill(pid, 0) for liveness checks needs cross-platform testing.

impl-6 Bottleneck

CLI node (impl-6) depends on all 5 core modules — it's the critical path. If any upstream impl fails, the CLI and engine integration are blocked. Consider splitting CLI into a thinner shell.
